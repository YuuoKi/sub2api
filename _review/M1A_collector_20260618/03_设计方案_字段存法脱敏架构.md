# 03 · 设计方案：字段 / 结果存法 / 脱敏 / 采集架构（四套，均带推荐）

> 对照判断基准：①服务 skill 飞轮 ②三级归因预留 ③脱敏硬红线 ④低侵入不破坏主路由 ⑤决策前置。

## 方案 1 · 字段方案（推荐版）

新独立表 `ai_generation_content`，每条 1:1 对应一次 usage_logs 记录（`(api_key_id, request_id)`）：

| 字段 | 类型 | 用途 | 对应基准 |
|---|---|---|---|
| `id` | BIGSERIAL PK | 主键 | — |
| `request_id` | VARCHAR(128) | 关联 usage_logs 的请求标识 | 归因② |
| `api_key_id` | BIGINT | 哪把 key（→员工） | 归因② |
| `user_id` | BIGINT | 哪个员工 | 归因②（员工✅） |
| `group_id` | BIGINT | 哪个团队/分组 | 归因②（团队✅） |
| `account_id` | BIGINT | 哪个上游账号 | 归因② |
| `model` | VARCHAR(255) | 用了哪个模型 | 分析 |
| `request_payload_hash` | VARCHAR(128) | 与 usage_logs 交叉去重核对 | 一致性 |
| `prompt_redacted` | TEXT | **脱敏后**的输入（燃料·输入） | 飞轮① |
| `response_redacted` | TEXT | **脱敏后**的产出（限容，燃料·产出） | 飞轮① |
| `prompt_bytes` | INT | 原始 prompt 字节数（脱敏/截断前） | 分析/监控 |
| `response_bytes` | INT | 客户端实收响应总字节（来自 `ForwardResult.ResponseBytes`） | 分析/监控 |
| `response_truncated` | BOOL | response 是否因超 cap 被截断 | 数据质量 |
| `redaction_version` | INT | 脱敏规则版本（规则变更即 bump，便于审计/回填） | 脱敏③ |
| **`task_id`** | BIGINT (预留) | 关联 drama/video 任务（M1 不写） | 飞轮①+归因②（任务❌→预留） |
| **`adoption_status`** | VARCHAR(32) (预留) | 采用/返工/废弃（M1 不写，M5/跨仓回流） | 飞轮①·质量信号 |
| **`quality_score`** | DECIMAL (预留) | 质量评分（M1 不写） | 飞轮①·质量信号 |
| `created_at` | TIMESTAMPTZ | 时间 | 时间 |

**归因缺口说明（基准2）**：现有 usage_logs 已覆盖 **员工(user_id/api_key_id)✅、团队(group_id)✅**，但**无"任务"维度**（无 task_id）。本表新增 `task_id` 预留位补齐"哪个任务"。
**质量信号说明（基准1）**：现系统的采用/返工/废弃信号目前只散在 drama 侧（`drama_gateway_service.go:174 ReuseStatus / :175 QualityScore / :241 ReviewStatus / :431 RecordDramaShotDecision`），**未与 usage_log 关联**；员工真实"采用/返工/废弃"动作来自 **QCanvas（独立仓，本次未侦察）**。M1 **只预留** `task_id`+`adoption_status`+`quality_score` 三列，**不在 M1 写入**，回流是后续里程碑（M5/跨仓）。

## 方案 2 · 结果存法（推荐：DB 直存 + 限容；超大走对象存储为后续可选）

| 选项 | 说明 | 评估 |
|---|---|---|
| **A（推荐）独立表 DB 直存 + 限容** | 文本直接入 `response_redacted TEXT`，超 64KiB 截断（`response_truncated=true`） | 最简单；结果形态以文本/URL 为主（见下），64KiB 覆盖绝大多数；满足基准4 |
| B 给 usage_logs 加列 | —— | ✗ 污染高频分区计费表（usage_logs 已分区 `migrations/035`、批量插入 64/256、有清理任务），且把计费保留期与内容/PII 保留期绑死。**淘汰** |
| C 独立表 + 超大走对象存储引用 | 超阈值大产出存 S3/MinIO，表里放引用 | 最抗大体积，但 M1 要先搭对象存储依赖，工程量更大 → **列为后续可选**，非 M1 首切 |

**结果形态实测（决定 64KiB 够不够）**：
| 类型 | 形态 | 量级 | 存法 |
|---|---|---|---|
| LLM 文本补全 | JSON content 文本块 | 0.1–50KB（多数 <64KiB） | 直存（超限截断） |
| 视频产出 | 单个 HTTPS URL（`VideoTask.ResultURL`） | <200B | 直存 |
| 图片产出 | URL 数组 / 计数尺寸 | <1KB | 直存 |
| 超长推理/上下文 | 大文本 | 10KB–1MB | 截断到 64KiB（`truncated=true`），如需全量走选项 C |

## 方案 3 · 脱敏方案（硬约束，基准3）：**入库前**脱敏，复用现有 + 补 PII

- **时机**：**采集前/入库前**脱敏（在 collector 内，落库前完成）——绝不先存原文再脱。
- **复用现有**（已生产验证）：
  - `backend/internal/util/logredact/redact.go:62/86` `RedactJSON`/`RedactText`（结构化敏感键：access_token/password/client_secret… + 自定义键）
  - `backend/internal/service/content_moderation_redact.go:20` `redactContentModerationSecrets`（Bearer/JWT/sk-前缀/长 hex/base64/URL/UUID 等 9 类）
  - （视频侧 `video_gateway_redact.go:121/137` 思路可借鉴）
- **调用顺序**：
  - prompt(JSON 体)：`RedactJSON` → `redactPII`(新增) → `redactContentModerationSecrets`
  - response(SSE/JSON 文本)：`RedactText` → `redactPII`(新增) → `redactContentModerationSecrets`
- **缺口（必须补）**：现有三套**都不覆盖自由文本 PII**（email/电话/证件）。新增最小 RE2 安全 pass（email + 保守电话正则；过度脱敏可接受，采集用于分析非保真）。
- **审计**：`redaction_version=1`，规则变更即 bump。**已知残留**：全字母凭据、12–19 字符不透明 token、正则外 PII 仍可能漏 → 配合保留期清理兜底（基准3 不追求 100%，追求"先脱、可演进、可清理"）。

## 方案 4 · 采集架构（推荐：异步旁路 + 限容 tee + fail-open，基准4）

- **挂载点**：复用现有异步旁路 `submitUsageRecordTask` 闭包（`gateway_handler.go:507`），在 `RecordUsage` 之后**并列**调用新 `contentCollector.Collect(...)`——**与计费隔离**（不进 `RecordUsageInput`、不进 `recordUsageCore`）。
- **prompt**：直接取闭包里的 `parsedReq.Body`（已在手）。
- **response**：新增 `cappedSink`（限容 tee）在 6 个 emit 出口抓客户端可见字节，回填 `ForwardResult.ResponseSample/ResponseTruncated/ResponseBytes`（首切先做出口 1+2 主流量，其余机械复用）。
- **fail-open 三重保险**（基准4 核心）：
  1. `cappedSink.Write` 永不报错、永不超额分配（写满即停）；
  2. `Collect` 自吞错误（warn 日志），DB/脱敏故障只丢这条采集、不抛；
  3. worker 池 `recover`（`gateway_handler.go:1844`）兜底 panic。
  → **采集任何失败/截断都不影响主调用与计费。**
- **kill switch**：配置 `gateway.content_capture.enabled` **默认 false**；关时不分配 sink、不调 collector，热路径**零开销**。
- **关键正确性**：`cappedSink` 必须持**全新 `[]byte`**，**绝不**复用池化 SSE 扫描缓冲（`getSSEScannerBuf64K`，`gateway_service.go:7180`）——否则归还后 use-after-return 损坏。
- **内存上界**：`并发流数 × response_max_bytes`（64KiB×2k 并发 ≈ 128MiB，有界可预测）。

> 落库表（非 ent）沿用 `content_moderation_logs` 先例：**裸 SQL migration + `database/sql` 仓，不走 ent schema/codegen**（append-only 旁路表无需 ent）。详见 [04](./04_改动清单_风险_回滚_验证.md)。
